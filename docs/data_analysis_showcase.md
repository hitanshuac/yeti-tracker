# Yeti-Tracker: Data Analysis Showcase

*This data presentation is structured in strict accordance with the Google Data Analytics Professional Certificate frameworks: APPASA, SMART, and PACE.*

---

## Phase 1: Ask
**Objective**: Define the business problem and establish clear, data-driven goals.

We defined the primary objective of the Yeti-Tracker using the **SMART** framework:
- **Specific**: Calculate total daily CO2 emissions for end-users based on real-time Merchant Category Code (MCC) transaction data.
- **Measurable**: Ensure analytical query latency remains under 1 second, and the tracking pipeline scales efficiently without exceeding a 10MB memory constraint.
- **Action-oriented**: Provide personalized category-level insights that drive immediate behavioral changes (e.g., reducing airline travel).
- **Relevant**: Addresses the growing demand for personal climate accountability.
- **Time-bound**: Deliver actionable insights on a rolling 30-day dashboard.

## Phase 2: Prepare
**Objective**: Determine how the data will be collected, stored, and managed.

To respect the $0 budget constraint and ensure extreme data privacy, we engineered a local, asynchronous Bronze ingestion layer (`src/bronze/async_generator.py`). 
- **Data Source**: Real-time mocked transaction payloads containing `amount_inr`, `mcc` (Merchant Category Code), and `timestamp`.
- **Storage**: Raw data is stored temporarily as un-tracked `.json` files to prevent Git bloat.
- **Ethics & Privacy**: By running processing entirely locally, user financial data never touches an external API.

## Phase 3: Process
**Objective**: Clean, transform, and validate the data to ensure integrity.

Our Silver layer (`src/silver/enrichment.py`) acts as the sanitation gateway.
- **Validation**: Incoming JSON payloads are strictly validated against Pydantic schemas. 
- **DLQ Routing**: Any corrupt payload (e.g., negative transaction amounts, malformed UUIDs) is automatically quarantined to a Parquet Dead Letter Queue (`quarantine_transactions.parquet`) for auditing.
- **Transformation**: Valid transactions are enriched by joining them with our static `emission_factors.json` map. We calculate `carbon_kg = amount_inr * kg_co2_per_inr`.

## Phase 4: Analyze
**Objective**: Discover insights using the **PACE** (Plan, Analyze, Construct, Execute) methodology.

We constructed our analytical models directly inside an embedded **DuckDB** instance. DuckDB provides massive column-store efficiency without the overhead of heavy distributed systems.

**Gold Layer Aggregation Example:**
```sql
SELECT 
    category,
    SUM(carbon_kg) as total_carbon_kg,
    COUNT(transaction_id) as total_transactions
FROM silver_transactions
GROUP BY category
ORDER BY total_carbon_kg DESC
```

## Phase 6: Act
**Objective**: Use the insights to drive data-driven decision-making.

By presenting this structured data to the end-user via our Glassmorphism UI dashboard, the user can visually identify that "Airlines" represent their highest emission factor despite only having 2 transactions. 
- **Action**: The user can set a SMART goal to reduce flight frequency by 50% next quarter, directly impacting their total carbon footprint.
